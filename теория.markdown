1. Docker — просто удобный способ запустить PosgresSQL.
2. Docker запускает программы в изолированных контейнерах, где уже есть всё нужное. Зачем это:

1. Ничего не нужно устанавливать в систему. Не нужно скачивать установщик PostgreSQL, проходить настройку, разбираться со службами Windows. Одна команда, и база работает. Не нужна — удаляешь контейнер, и в системе не остаётся мусора.
2. Одинаково у всех. Файл docker-compose.yml описывает, какая база, какая версия, с какими настройками. Другой разработчик или проверяющий берёт твой проект, запускает docker compose up, и у него та же самая база, что у тебя. Без инструкций вида «установи PostgreSQL версии такой-то и настрой так-то».
3. Легко менять версии и начинать заново. Нужна другая версия — меняешь цифру в image. Сломала базу — удаляешь контейнер и volume и поднимаешь чистую.

**Образ** — это шаблон, готовая «упаковка» программы со всем нужным для её работы. Сам по себе он ничего не делает, он просто лежит. Он доступен только для чтения: изменить его в процессе работы нельзя.

**Контейнер** — это запущенный экземпляр образа. Он работает, в нём что-то происходит, в него пишутся файлы.
**Volume** — это хранилище, которое Docker держит отдельно от контейнера. Ты подключаешь его к папке, куда PostgreSQL пишет данные. Тогда данные на самом деле лежат в volume, а не в контейнере. Контейнер можно удалить и создать заново — новый подключится к тому же volume и увидит все старые данные.

**Миграция** делает ровно одно маленькое изменение (добавляет колонку), а данные остаются. Это ты и проверяешь в задании пунктом «старые задачи должны остаться».

*alembic init migrations* - создаёт папку для миграций и файлы настройки: alembic.ini, env.py, script.py.mako, versions/. Выполняется один раз на проект. С флагом -t async создаёт шаблон под асинхронный драйвер.

*alembic current* показывает, на какой миграции сейчас база. Удобно проверять, что подключение работает.

*alembic revision --autogenerate -m "..."* сравнивает модели с реальной базой и создаёт файл миграции с разницей. В базе при этом ничего не меняется, просто появляется файл. -m задаёт описание.

*alembic upgrade head* применяет все ещё не применённые миграции, до самой последней.

*alembic downgrade -1* откатывает одну последнюю миграцию, то есть выполняет её downgrade().

*alembic history* показывает всю цепочку миграций по порядку.

без миграций не поллучится мменять схему существуюей базы! а также они позволяют откатить изменения

Поэтому в REST принято так: **у каждой сущности свой адрес**. /tasks для задач, /sessions для сессий, /categories для категорий, как у тебя уже есть. Каждую можно создавать, читать и удалять отдельно.

А **связь между ними** показывает GET /tasks/{task_id}/sessions: «дай сессии вот этой задачи». Адрес сразу читается: сессии, принадлежащие задаче.
